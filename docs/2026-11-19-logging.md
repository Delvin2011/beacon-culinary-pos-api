# Logging (T0-1)

How POS_BE logs: the fields every line carries, the format in each environment, how to change log levels, how to find a request in Azure, and what is never logged.

The code is in `src/main/java/com/beaconculinary/api/common/logging/`.

## 1. Formats per profile

| Profile | Console output | Set by |
|---|---|---|
| `prod` | **Logstash JSON**: one object per line on stdout, which Azure collects | `application-prod.yaml`: `logging.structured.format.console: logstash` |
| `dev`, and the tests (default profile) | Readable text, with `[requestId or jobName] [userId]` after the level | `application.yaml`: `logging.pattern.level` |

A production line for a request:

```json
{"@timestamp":"2026-11-19T15:55:13.236+02:00","@version":"1","message":"request POST \/orders status=201 durationMs=42 host=beaconculinary.pos.localhost","logger_name":"com.beaconculinary.api.common.logging.RequestContextFilter","thread_name":"http-nio-8080-exec-3","level":"INFO","level_value":20000,"deviceId":"5d62fd01-…","method":"POST","path":"\/orders","requestId":"3f2b9c1e-6a7d-4c1f-9b2e-1d5a8e7c0f42","role":"CASHIER","route":"\/orders","sessionId":"9d1c…","tenantId":"default","tillCode":"T1","userId":"12","status":201,"durationMs":42,"host":"beaconculinary.pos.localhost"}
```

An alert line:

```json
{"@timestamp":"…","@version":"1","message":"LOGIN_PROTECTION_ALERT type=SELF_UNLOCK_REFUSED reason=… user=12","logger_name":"com.beaconculinary.api.auth.protection.LoginAttemptService","thread_name":"…","level":"WARN","level_value":30000,"tags":["LOGIN_PROTECTION_ALERT"]}
```

The same request line in text (dev):

```
2026-11-19T15:55:13.236+02:00  INFO [3f2b9c1e-…] [12] … c.b.a.c.logging.RequestContextFilter : request POST /orders status=201 durationMs=42 host=beaconculinary.pos.localhost
```

An exception stays on one JSON line, in the `stack_trace` field.

## 2. Fields

**Standard (every line):** `@timestamp`, `level`, `logger_name`, `thread_name`, `message`; `stack_trace` when there is an exception.

**Request lines.** Set for the whole request by `RequestContextFilter`, the first filter (before Spring Security):

| Field | Meaning | Set by |
|---|---|---|
| `requestId` | The request's id. A safe inbound `X-Request-Id` is kept (pattern `^[A-Za-z0-9._-]{8,64}$`); anything else is replaced by a new UUID. Always returned in the `X-Request-Id` response header (CORS exposes it) | `RequestContextFilter` |
| `tenantId` | `default` in single mode. In multi mode the customer's slug: for every request, from its address (T1-3, `CustomerResolutionFilter`; the request line too), and while `CustomerContext` is set (T1-2) | `RequestContextFilter`, `JobContext`, `CustomerContext` |
| `method`, `path` | HTTP method and path. **Never the query string** | `RequestContextFilter` |
| `route` | The matched route pattern, e.g. `/admin/sale-exceptions/{id}`. Blank when no handler matched (a 401 or 404 before Spring MVC) | `RequestContextFilter`, at the end |
| `userId`, `role` | The signed-in user, once a valid access token is accepted | `JwtAuthenticationFilter` |
| `sessionId` | The token's `sid` claim: the session's id, not a credential | `JwtAuthenticationFilter` |
| `deviceId`, `tillCode` | The till whose `deviceToken` cookie matched, including revoked or expired tills. Never the cookie | `DeviceResolutionFilter` |

The MDC is cleared in `finally` at the end of every request, so nothing carries over to the next request on the same thread.

**The request log line.** One INFO line per request, from `RequestContextFilter`, written last (so it has every field above), including requests refused with 401 or 403:

```
request {method} {route or path} status={status} durationMs={ms} host={host}
```

In JSON, `status` and `durationMs` are also numeric fields, and `host` is a field.

**`host` (T1-L0)** is the address the browser used. Behind a proxy (the local stack's Caddy, later Front Door) it is `X-Forwarded-Host`, believed only when the direct peer is in `security.login-protection.trusted-proxies` (the same list that decides whether `X-Forwarded-For` is believed); otherwise it is the `Host` header. It is lower-cased, the left-most entry when a chain appended several, and `invalid` when it isn't a plain host name with an optional port, so a client can't write arbitrary text into the log. `-` when there is none.

There is no request line for:
- the paths in `logging.request.skip-paths`: `/health` (tills poll it every few seconds) and `/**/stream` (the kitchen, bar and board SSE streams). Override with the `LOGGING_REQUEST_SKIP_PATHS` environment variable (comma-separated Ant patterns);
- CORS preflights (`OPTIONS`).

Skipped requests still get a `requestId` and the response header.

**Background lines.** Set for one run by `JobContext`:

| Field | Meaning |
|---|---|
| `jobName` | `login-attempt-retention` (daily 03:30), `session-sweep` (every minute), `health-check` (the database probe on the `health-db-check` thread) |
| `runId` | 8 hex characters, new for each run |
| `tenantId` | `default`; in multi mode the customer's slug, since jobs run once per customer (T1-2, `CustomerJobs`) |

Each run writes `job {name} finished durationMs=…` at DEBUG; a run that throws is logged once at ERROR. The session sweep logs at INFO only when it ended sessions. The health check's two state-change lines ("database reachable" / "not reachable") carry `source=health-check`.

**Markers (`tags` in JSON):**

| Tag | Lines |
|---|---|
| `LOGIN_PROTECTION_ALERT` | Login-protection alerts (`LoginAttemptService`) and device-trust alerts (`DeviceAlerts`) |
| `DEVICE_UNBOUND_TILL_REQUEST` | A cashier's order or shift request from a browser that is not a registered till (`DeviceUnboundRequestFilter`) |

The tag name also stays as the first word of the message, so existing text searches keep working.

## 3. Log levels

Defaults in `application.yaml`: `root` and `com.beaconculinary` at INFO. In `dev`, `spring.jpa.show-sql` prints SQL statements (without parameter values) straight to stdout, not through the logger, so those lines have no fields; it is off outside `dev`.

Change a level per environment with an environment variable (Spring's relaxed binding: dots become underscores, upper case):

| To | Set |
|---|---|
| Debug the whole app | `LOGGING_LEVEL_COM_BEACONCULINARY=DEBUG` |
| Debug one package, e.g. device trust | `LOGGING_LEVEL_COM_BEACONCULINARY_API_DEVICES=DEBUG` |
| See each job's "finished" line | `LOGGING_LEVEL_COM_BEACONCULINARY_API_COMMON_LOGGING=DEBUG` |
| Quieten a noisy library | `LOGGING_LEVEL_ORG_HIBERNATE=WARN` |

The app needs a restart to pick up a change. Don't turn on DEBUG for `org.springframework.web` or `org.apache.tomcat` in production (see section 5).

## 4. Finding things in Azure

Azure collects stdout. The table and column depend on the hosting service. **Container Apps:** table `ContainerAppConsoleLogs_CL`, column `Log_s` (or `ContainerAppConsoleLogs`, column `Log`, with the newer schema). **App Service:** table `AppServiceConsoleLogs`, column `ResultDescription`. The examples use Container Apps; swap the table and column for App Service.

One request, by the id a user or the frontend reported (the `X-Request-Id` response header):

```kusto
ContainerAppConsoleLogs_CL
| where Log_s has "3f2b9c1e-6a7d-4c1f-9b2e-1d5a8e7c0f42"
| extend j = parse_json(Log_s)
| project TimeGenerated, level = tostring(j.level), logger = tostring(j.logger_name), message = tostring(j.message), j
| order by TimeGenerated asc
```

Everything one till did in the last hour:

```kusto
ContainerAppConsoleLogs_CL
| where TimeGenerated > ago(1h)
| extend j = parse_json(Log_s)
| where tostring(j.tillCode) == "T1"
| project TimeGenerated, message = tostring(j.message), userId = tostring(j.userId), requestId = tostring(j.requestId)
```

Slow or failing requests:

```kusto
ContainerAppConsoleLogs_CL
| extend j = parse_json(Log_s)
| where tostring(j.logger_name) endswith "RequestContextFilter"
| where toint(j.status) >= 500 or toint(j.durationMs) > 2000
| project TimeGenerated, route = tostring(j.route), status = toint(j.status), durationMs = toint(j.durationMs), requestId = tostring(j.requestId)
```

Alerts (use as an Azure Monitor log alert rule):

```kusto
ContainerAppConsoleLogs_CL
| extend j = parse_json(Log_s)
| where j.tags has "LOGIN_PROTECTION_ALERT"
| project TimeGenerated, message = tostring(j.message)
```

One customer's requests, and requests and errors per customer (multi mode):

```kusto
ContainerAppConsoleLogs_CL
| extend j = parse_json(Log_s)
| where tostring(j.logger_name) endswith "RequestContextFilter" and tostring(j.tenantId) == "beaconculinary"
| project TimeGenerated, route = tostring(j.route), status = toint(j.status), requestId = tostring(j.requestId)
```

```kusto
ContainerAppConsoleLogs_CL
| extend j = parse_json(Log_s)
| where tostring(j.logger_name) endswith "RequestContextFilter"
| summarize requests = count(), errors = countif(toint(j.status) >= 500) by customer = tostring(j.tenantId), bin(TimeGenerated, 1h)
```

One job run:

```kusto
ContainerAppConsoleLogs_CL
| extend j = parse_json(Log_s)
| where tostring(j.jobName) == "session-sweep"
| summarize lines = count(), first = min(TimeGenerated) by runId = tostring(j.runId)
```

## 5. Never log

None of these may appear in a log line, at any level:

- `Authorization` headers and access tokens (JWTs)
- Cookies: `refreshToken`, `deviceToken` (log the device's id and till code instead)
- Passwords, PINs, manager-PIN authorisation tokens and session tokens
- Invite tokens and links (T0-6a). They travel only in request bodies (`POST /auth/invites/lookup`, `/accept`) and after `#` in the link, never in a path or query. The database keeps only their SHA-256, and log lines name the invite by id (`invite=`, `invite:<id>`)
- Offline grant strings and signing keys; the offline unlock value (it never reaches the server, which only receives `unlockedOffline` as true or false)
- Request and response bodies
- Query strings (log the path or route)
- Connection strings, the JWT secret and any other secret from configuration
- Secret values from `SecretResolver` (T1-1): a missing secret is reported by its name and environment variable only. The platform database's password, and the customer database logins' passwords the devstack scripts pass to `sqlcmd`
- Email addresses in clear: login protection logs them hashed (`sha256:` prefix) and keeps doing so

How this is kept:
- `RequestContextFilter` logs only the method, path, route, status and duration, and the MDC fields above.
- `spring.mvc.log-request-details` stays `false` (the default), and Spring Web and Tomcat stay above DEBUG in production; at DEBUG they can print headers.
- Tests: `RequestLogFieldsIntegrationTests` captures all log output across password sign-in, PIN sign-in (right and wrong), refresh, the offline grant and offline sync, and fails if any password, PIN, token, cookie value or grant string appears. `NoConsolePrintingTest` fails if `System.out`, `System.err` or `printStackTrace` appears in `src/main/java`.

- T0-6a: `InviteIntegrationTests` and `FirstAdminCommandIntegrationTests` fail if an invite token, its hash, a password or a PIN appears in the log output. The operator's first-admin command (`ops/FirstAdminCommand`) is the one class allowed to print to the console: it runs from a terminal, never inside the app, and prints the link only there. `NoConsolePrintingTest` allows exactly that file and checks that nothing in the app refers to it.

- T1-1: `TenancyProperties` reports bad settings by name, never value, and has no `toString` with the password; `TenancyModeIntegrationTests`, `EnvironmentSecretResolverTest` and `TenantRegisterCommandIntegrationTests` fail if a password or secret value appears in the output. `TenantRegisterCommand` is allowed to print (an operator's terminal command, like `FirstAdminCommand`) and prints secret names only. Multi mode logs two start-up lines, `tenancy multi: platform database at version N ...` and `tenancy multi: customer directory loaded, N customer(s), M active` (fields `customers`, `activeCustomers`).

- T1-2, multi mode: a customer's pool logs `tenancy: customer <slug> pool opened (database … on …), schema at version N` on its first connection and `… pool closed (<reason>)` when closed; credentials never appear (they go to the pool from `SecretResolver`, and the JDBC URL holds none). A job that fails for one customer logs `job <name> failed for customer <slug>; the other customers' runs go on`. `CustomerPoolsIntegrationTests`, `MultiModeStartupIntegrationTests` and `MultiCustomerIsolationIntegrationTests` fail if a password or secret value appears in the output.

When adding a log line: use an SLF4J logger, log ids rather than values, and never pass a request, header map, cookie or DTO that may hold a secret as an argument.
